# 技术栈选择决策树

> 基于项目需求、团队技能、成本约束的全面技术栈选择框架

---

## 使用指南

**适用场景**:
- 项目初期的技术栈选型
- 技术重构的框架选择
- 新产品线的架构决策

**使用方式**:
```
/hbe:architect "我需要做一个 [项目类型]，团队擅长 [语言]，[约束条件]"
```

## 决策流程

```
Step 1: 确定项目类型
    ↓

## Step 1: 确定项目类型

### 项目类型分类

| 类型 | 特征 | 典型例子 |
|------|------|----------|
| **Web 应用** | B/S 架构，用户通过浏览器访问 | 电商、SaaS、管理系统 |
| **移动应用** | 原生 App，跨平台 | iOS/Android App |
| **CLI 工具** | 命令行工具，单文件分发 | 开发工具、系统工具 |
| **库/SDK** | 代码库，供其他项目使用 | React 库、Python SDK |
| **桌面应用** | 桌面软件，本地运行 | 编辑器、IDE 插件 |
| **API 服务** | RESTful/GraphQL API | 微服务、BFF |
| **数据处理** | ETL、数据分析、报表 | 数据管道、BI 工具 |
| **机器学习** | 模型训练、推理服务 | CV、NLP、推荐系统 |

---

## Step 2: 团队技能评估

### 评估矩阵

```
团队规模 × 技能熟练度 = 技术选择策略
```

| 团队规模 | 全栈专家 | 单栈专家 | 新手团队 | 混合团队 |
|---------|---------|---------|---------|---------|
| **1-2 人** | 选择最熟悉的 | 选择专精技术 | 选择低学习曲线 | 选择通用语言 |
| **3-5 人** | 可探索新技术 | 深度优化专精 | 选择成熟框架 | 跨语言协作 |
| **5+ 人** | 考虑协作成本 | 微服务/领域拆分 | 选择企业级框架 | 需要架构师 |

### 技能熟练度定义

- **专家**: 3+ 年生产经验，深层理解原理
- **熟练**: 1-3 年经验，能独立完成项目
- **新手**: <1 年经验，需要指导和学习

---

## Step 3: 约束条件分析

### 常见约束

| 约束类型 | 影响 | 权衡 |
|---------|------|------|
| **时间** | 紧急 → 选熟悉的 | 宽松 → 可探索 |
| **预算** | 有限 → 开源/免费 | 充足 → 商业方案 |
| **性能** | 高性能 → 编译型 | 一般 → 解释型 |
| **安全** | 金融级 → 静态类型 | 一般 → 动态类型 |
| **合规** | 等保 3 级 → 国产化 | 无要求 → 国际化 |
| **团队** | 小团队 → 简化技术 | 大团队 → 成熟技术 |

## 技术栈推荐矩阵

### 🌐 Web 应用

#### 小型项目（MVP、原型）

| 团队技能 | 推荐技术栈 |
|---------|-----------|
| **JavaScript 全栈** | Next.js + TailwindCSS + Vercel |
| **Python 全栈** | Django + HTMX + Railway |
| **PHP** | Laravel + Inertia.js |

**理由**: 快速开发、学习曲线低、部署简单。

**理由**: 平衡性能和开发效率、生态成熟。

**理由**: 高性能、可扩展、微服务架构。

## 数据库选择

### 决策树

```
数据结构
  ├─ 关系型 → PostgreSQL（首选）/ MySQL
  ├─ 文档型 → MongoDB
  ├─ 键值型 → Redis / Memcached
  ├─ 时序型 → InfluxDB / TimescaleDB
  ├─ 搜索型 → Elasticsearch / Meilisearch
  └─ 图形 → Neo4j
```

### 详细对比

| 数据库 | 类型 | 优点 | 缺点 | 推荐场景 |
|--------|------|------|------|----------|
| **PostgreSQL** | 关系型 | 功能丰富、扩展性强 | 复杂查询慢 | 复杂业务、事务 |
| **MySQL** | 关系型 | 性能好、生态成熟 | JSON 支持弱 | 简单 CRUD |
| **MongoDB** | 文档型 | Schema 灵活 | 事务支持弱 | 快速迭代 |
| **Redis** | 键值 | 高性能、数据结构丰富 | 持久化复杂 | 缓存、会话 |
| **Elasticsearch** | 搜索 | 全文搜索强大 | 资源占用大 | 搜索服务 |

## 快速决策工具

### 决策树问答

```
Q1: 项目类型是什么？
→ Web / 移动 / CLI / 库 / API / 数据 / ML

→ 1-2 人 / 3-5 人 / 5+ 人

Q3: 时间压力？
→ 紧急（1 月）→ 选熟悉的

Q4: 性能要求？

Q5: 预算约束？
→ 紧张 → 开源 + 云服务
→ 充足 → 商业方案

Q6: 安全要求？

## 行业最佳实践

### 金融行业

**要求**: 安全性、合规性、可靠性

**推荐技术栈**:
- 后端: Java + Spring Boot / Go + gRPC
- 数据库: PostgreSQL + Redis
- 消息队列: Kafka / RabbitMQ
- 监控: Prometheus + Grafana

### 电商行业

**要求**: 高并发、可扩展、稳定性

**推荐技术栈**:
- 后端: Go + Gin / Node.js + NestJS
- 缓存: Redis
- 数据库: PostgreSQL + Redis
- CDN: Cloudflare

### 初创公司

**要求**: 快速迭代、成本控制

**推荐技术栈**:
- 全栈: Next.js + PostgreSQL + Vercel
- 后端: Python + FastAPI
- 认证: Clerk / Auth0
- 监控: Sentry

### 企业内部工具

**要求**: 开发效率、维护性

**推荐技术栈**:
- 后端: Python + FastAPI / Java + Spring Boot
- 前端: React / Vue
- 认证: SSO / LDAP
- 部署: Docker + Kubernetes

## 总结

### 技术栈选择三原则

1. **适合团队** - 技能匹配比技术先进更重要
2. **适合场景** - 不同场景有最优解
3. **适合未来** - 考虑可扩展性和维护性
